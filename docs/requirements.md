## 1. 产品定义

JobPicky 是一个以后端能力为主的岗位聚合与个性化推荐系统。它从企业官方招聘入口建立可追溯、可更新的岗位库，再根据求职者的简历和求职偏好生成可信、可解释的岗位候选。

系统解决两个核心问题：

1. 企业岗位散落在不同 ATS 和自建招聘网站中，格式不统一、更新状态难以判断。
2. 关键词搜索不能充分理解求职者经历与岗位要求，但完全交给大模型又容易产生事实错误和不可复现的结果。

产品价值不在于“抓取所有网站”或“让 Agent 自由行动”，而在于：

- 岗位来自可追溯的官方来源；
- 明确条件不会被推荐逻辑忽略；
- 推荐理由能对应真实简历和真实 JD；
- 采集或推荐失败时，系统不会伪装成功或破坏已有数据。

## 2. 使用者与关键场景

### 2.1 求职者

求职者需要：

- 提交简历文本或文件，并补充自然语言求职要求；
- 查看和修正系统提取的结构化画像；
- 发起推荐并查看运行状态；
- 查看包含真实岗位事实、匹配理由和能力缺口的推荐结果；
- 进入官方详情页或投递页；
- 在后续版本中保存、忽略或标记已投递岗位。

### 2.2 运营或维护者

运营或维护者需要：

- 录入公司名称和官方招聘入口；
- 触发采集并判断一次运行是成功、部分成功还是失败；
- 查看岗位数量、字段完整性、异常下降和失败原因；
- 识别不支持或规则失效的网站，并重新配置、重新探索或人工介入；
- 查看推荐运行的阶段、耗时和失败原因，但默认看不到完整简历和敏感信息。

### 2.3 外部客户端

未来的用户端和后台管理端是独立客户端，共享同一后端。MVP 不要求实现 UI，但后端必须提供稳定、版本化且边界清晰的用户接口与管理接口。

## 3. MVP 范围

### 3.1 P0：首个可用闭环

#### 岗位采集与岗位库

- 管理公司名称和官方招聘入口，支持启用、停用和手动触发采集。
- 通过可复用的采集器或平台适配器处理已知招聘平台。
- 以真实样本驱动首批平台支持。飞书招聘、北森和 Moka 是优先候选，但实现顺序由现有公司样本和验证成本决定。
- 至少打通一个主流 ATS 的完整分页、岗位详情和投递链接；MVP 验收时至少覆盖三种有代表性的来源或采集方式，其中至少包含一个共享 ATS 和一种非同构来源。
- 将不同来源转换为统一岗位事实，并保存来源、最近确认时间和采集运行关联。
- 重复采集保持幂等；岗位内容变化可以更新；一次不完整采集不得批量关闭未出现的历史岗位。
- 对不支持、需要登录、被访问控制阻断或无法确认完整性的来源给出明确状态和可操作原因。
- 支持按状态、公司、城市和关键词查询岗位。

#### 用户画像与推荐

- 接收简历文本，并通过可替换的文本提取层支持至少一种常见简历文件格式；具体格式按首批用户样本确定。
- 将简历和补充要求解析为可查看、可修改、可版本化的结构化画像。
- 确定性执行开放状态、城市、招聘类型、学历、届次、期望薪资下限和明确排除岗位等硬条件；信息不足时不得擅自推断为不符合，岗位未标明届次或薪资时不得因此排除。
- 同时具备精确关键词召回和语义召回能力；两种召回方式可独立验证，融合策略可以迭代。
- 使用大模型判断候选岗位与用户经历、技能和目标方向的匹配程度，并输出结构化结果。
- 最终推荐由系统岗位事实与模型评估结果组装。模型不得生成或修改公司、岗位名称、JD、城市和链接。
- 保存推荐运行、所用画像版本、候选结果、评估结果和失败信息。

#### 服务接口与运行保障

- 提供 `/api/v1` 下最小用户接口、管理接口和健康检查；具体契约以 `architecture.md` 为准。
- 采集和推荐作为长任务执行，创建后返回运行标识，并可查询状态与结果。
- 提供 OpenAPI，客户端不需要了解采集、检索、模型或工作流内部实现。
- 记录可定位问题的结构化运行信息，同时避免记录密钥、完整简历和不必要的模型敏感输入。
- 提供数据库迁移、配置校验和可运行的自动化测试基线。

### 3.2 P1：首版增强

- 补齐飞书招聘、北森、Moka 中尚未覆盖的平台，并继续按真实来源价值增加适配器。
- 对未知网站尝试发现岗位入口、接口、分页和字段映射；验证成功后保存为可复用配置。
- 在无稳定接口时提供通用 API 或 HTML 采集兜底。无法可靠采集时允许转人工处理，不承诺对任意网站全自动适配。
- 支持定时采集、有限重试、规则失效检测和重新探索。
- 支持用户查看、收藏、忽略和标记已投递岗位。
- 支持后台查看数据质量、采集趋势和推荐运行摘要。
- 支持服务重启后的任务恢复或可安全重跑，避免产生重复业务结果。
- 建立更完整的真实网站样本集和人工标注的推荐评估集。

### 3.3 Later：当前不做

- 用户端或后台管理端的 UI、视觉规范和具体页面交互。
- 自动投递简历或代替用户执行外部网站操作。
- 登录、验证码破解、反爬绕过或绕过网站访问控制。
- 面向大规模多租户的复杂权限系统。
- 多 Agent 自由协商、自主创建工具或自主修改工作流。
- 微服务、分布式消息平台和为未知规模提前建设的基础设施。
- 在线学习、Learning to Rank、自动修改简历和基于用户反馈自动改模型。
- 对所有未知网站的成功率承诺。

## 4. 必须遵守的业务规则

以下规则是跨实现的产品边界，不得为了简化代码而弱化。

### R1. 岗位事实可追溯

每个可推荐岗位必须能够追溯到公司招聘源和最近一次有效采集。最终展示的公司、岗位名称、JD、城市、详情链接和投递链接来自岗位库，而不是模型记忆或临时生成。

### R2. 不确定性必须显式表达

无法确认的字段使用缺失或 `UNKNOWN` 语义；无法确认完整性的采集使用部分成功或失败状态。系统不得用看似完整的默认值掩盖未知信息。

### R3. 硬条件由确定性逻辑执行

开放状态、用户明确排除项及其他可结构化的强约束由程序执行并可复现。大模型可以帮助理解自然语言，但不能覆盖已确认的硬条件。

### R4. 不完整采集不得关闭历史岗位

只有当系统能确认分页、详情请求和结果完整性时，才可以将本次未出现的旧岗位视为关闭。数量异常下降、分页失败、解析异常或来源不可用时，已有岗位保持原状态或进入待确认状态。

### R5. 重复执行必须安全

同一来源重复采集、同一任务重试以及客户端重复提交，不应产生重复岗位或重复推荐结果。无法完全幂等的外部步骤必须在业务写入前去重。

### R6. 模型输出不是事实来源

画像解析和岗位评估的模型输出必须经过结构校验。模型只能引用输入中的用户事实和岗位事实；无依据时应说明信息不足，不能补写经历、岗位要求或链接。

### R7. 推荐绑定画像版本

画像修改后生成可区分的新版本。一次推荐必须能够说明使用了哪个画像版本和哪些岗位事实版本，避免历史结果随当前画像或岗位内容静默变化。

### R8. 用户数据和管理数据隔离

用户只能访问自己的画像、运行结果和个人岗位状态。管理端可以查看运行与质量信息，但默认不返回完整简历、联系方式、模型提示词、Cookie、Token、原始内部响应和错误堆栈。

### R9. 外部访问保持合规和克制

采集仅针对公开的官方招聘入口，设置超时、并发和频率边界，遵守适用的网站条款和访问限制。遇到登录、验证码或明确拒绝访问时停止并报告，不尝试绕过。

## 5. 能力要求

### 5.1 招聘源与采集

一个招聘源至少包含公司身份和官方招聘入口。系统应能解析跳转后的实际入口，识别可复用的平台能力，并将“平台通用逻辑”和“公司特定参数”分离。

一次采集应产生：

- 运行状态和采集方式；
- 发现、有效、新增、更新及可能关闭的岗位数量；
- 是否可确认完整；
- 警告、失败阶段和可操作错误；
- 标准化岗位集合或其持久化结果。

平台内部接口、浏览器探索、HTML 解析或其他方法都只是实现手段。实现应优先复用稳定接口；只有发现或修复规则时才承担浏览器成本。

### 5.2 岗位事实与生命周期

岗位事实至少覆盖公司、企业性质、岗位名称、工作地点、JD、详情链接、投递链接、招聘类型、学历要求、薪资范围、届次限定、来源身份、开放状态和时间信息。具体字段名与类型由 `architecture.md` 固定。薪资、届次与企业性质无法确认时保持未知，不得伪造。

岗位身份判定应优先使用来源提供的稳定岗位 ID，其次使用稳定详情地址，再使用足以区分岗位的规范化组合。具体哈希算法和数据库约束属于内部实现，只需满足稳定、可解释和可迁移。

岗位库需要区分：

- 首次发现；
- 最近确认仍存在；
- 内容更新；
- 已确认关闭；
- 暂时无法确认。

### 5.3 用户画像

画像需要表达：

- 目标城市与岗位方向；
- 技能；
- 明确排除项；
- 学历；
- 届次（校招场景）；
- 期望薪资下限；
- 与匹配有关的经历或项目摘要；
- 用户补充要求；
- 缺失项和解析警告。

用户应能修正关键字段。原始简历解析与画像提取应解耦，以便替换文件解析器或模型而不改变后续推荐契约。

### 5.4 过滤、召回与评估

推荐链路按以下职责顺序工作：

```text
读取画像和本次补充要求
→ 执行硬条件过滤
→ 使用关键词与语义能力召回候选
→ 读取候选岗位事实
→ 评估匹配程度
→ 再次以岗位事实组装并保存结果
```

召回应倾向于保留可能相关的岗位，精排负责排除语义误召回并解释优势与缺口。候选数量、阈值、分数融合和批处理方式应通过评估集调整，不在需求中固定算法。

每条最终结果至少能回答：

- 为什么推荐或不推荐；
- 哪些技能或经历形成匹配；
- 哪些要求缺乏证据或存在缺口；
- 岗位事实来自哪里；
- 本次判断使用了什么版本的画像和模型配置。

### 5.5 工作流编排

推荐过程必须是有边界、可观测的工作流。每个阶段有明确输入、输出和失败状态，外部服务错误只做有限重试。

LangChain 和 LangGraph 是优先实现方向：前者可封装模型、工具和结构化输出，后者可表达状态图、检查点和恢复。但验收关注受控执行、可测试、可追踪和可替换，而不是为了使用框架增加没有业务价值的 Agent 层。

工作流状态或检查点不是正式业务结果的唯一存储。运行状态与推荐结果必须保存到业务数据存储中。

### 5.6 用户接口与管理接口

用户接口至少支持：

- 创建或更新画像；
- 查询当前画像；
- 发起推荐；
- 查询推荐状态与结果；
- 查询结果对应的岗位事实。

管理接口至少支持：

- 管理招聘源；
- 触发并查询采集运行；
- 查询岗位及数据质量信息；
- 查询推荐运行摘要和失败原因。

身份系统可以从本地单用户模式起步，但用户和管理员上下文在接口层必须明确存在，不能通过“所有请求默认是管理员”完成 MVP。

### 5.7 运行、配置与可观测性

- 外部 HTTP、浏览器、Embedding 和大模型调用都有超时和有限重试。
- 运行使用统一标识串联日志、状态和结果。
- 关键配置在启动时校验，秘密通过环境或等价的安全配置来源提供。
- 长任务不阻塞普通查询；具体 Worker、队列和调度方案按实际规模选择。
- 错误信息对用户可理解，对维护者可定位，但不泄露敏感数据。

## 6. 非功能要求

### 6.1 正确性优先

错误推荐可以被解释和修正，错误关闭大量岗位则可能造成数据丢失。因此岗位同步和事实来源的正确性优先于采集速度、推荐速度和自动化程度。

### 6.2 可测试性

- 平台识别、分页、标准化、去重、硬筛选、输出校验和结果组装可以离线测试。
- 外部网站测试与普通 CI 分离，避免网络波动使主测试失去可信度。
- 模型与 Embedding 调用可以替换为测试实现。
- 每个关键失败分支至少有一种可重复验证方式。

### 6.3 可演进性

新增同一 ATS 的公司通常只增加配置；新增平台只增加对应采集能力。替换数据库访问、模型厂商、Embedding 模型、任务执行器或编排框架时，不应改变客户端接口和核心业务语义。

### 6.4 成本与性能

MVP 不设脱离真实数据的固定毫秒指标。实现必须避免无界并发、无界候选集、无限重试和对每次采集都启动浏览器。建立真实运行基线后，再为延迟、吞吐和单次模型成本设预算。

## 7. 验收场景

### A. 已支持来源完整采集

给定一个包含多页岗位、独立详情请求和不同投递链接的真实或脱敏离线样本：

- 系统得到与黄金数据一致的岗位身份和核心事实；
- 再次运行不产生重复岗位；
- 某个岗位内容变化时更新同一岗位；
- 完整运行中确实消失的岗位可以被关闭。

### B. 不完整采集保护

给定分页中断、详情大量失败或岗位数量异常下降：

- 运行被标记为部分成功或失败；
- 已成功获取的岗位可以安全写入；
- 未出现的历史岗位不会被批量关闭；
- 维护者能看到失败阶段和原因。

### C. 未知或不支持来源

给定一个未支持来源：

- 系统能够尝试识别或探索，或明确返回“不支持/需人工处理”；
- 未验证的探索结果不会直接成为正式同步规则；
- 验证成功的规则在后续运行中可以复用。

自动探索和复用属于 P1；P0 至少必须保证失败可控且不污染岗位库。

### D. 推荐闭环

给定一份画像和一组包含明确匹配、语义近似、硬条件冲突及信息不足的岗位：

- 硬条件冲突岗位不会进入最终推荐；
- 关键词和语义召回都能贡献可追溯候选；
- 模型非法输出不会写入正式结果；
- 每条最终结果的岗位事实与岗位库一致；
- 推荐理由、匹配项和缺口都能在输入事实中找到依据。

### E. 接口和数据边界

- 客户端可通过运行标识查询长任务，不依赖内部节点实现。
- 用户上下文不能读取其他用户数据或管理数据。
- 管理端默认看不到完整简历和秘密采集配置。
- 主要接口能由 OpenAPI 和契约测试验证。

## 8. 质量度量

数字指标必须基于版本化的测试集，不能用少量成功样本推断整体质量。

### 8.1 硬性质量门槛

- 不完整采集场景中，错误关闭历史岗位数为 **0**。
- 最终推荐中，违反已确认硬条件的岗位数为 **0**。
- 最终推荐中的岗位 ID、公司、标题、JD 和链接均能关联岗位库中的事实记录。
- 非法模型结构、未知岗位 ID 和重复岗位 ID不会进入正式结果。
- 密钥、Cookie、完整简历和联系方式不会出现在普通日志或公开接口中。

### 8.2 持续评估指标

采集侧至少跟踪：

- 来源识别成功率；
- 完整采集成功率；
- 岗位召回与分页完整性；
- 核心字段完整率；
- 详情链接和投递链接准确率；
- 异常下降及误关闭数量。

推荐侧至少跟踪：

- 画像结构通过率与人工修正率；
- 硬筛选正确率；
- 候选召回率；
- 人工标注集上的 Precision@K 或等价 Top-K 指标；
- 推荐理由事实一致性；
- 非法输出率、运行耗时和模型成本。

已支持平台、未知网站和受访问限制网站分别统计。首批基线建立后，在评估配置或发布计划中确定数值目标，不把尚未验证的百分比写成需求事实。

## 9. 开发前需要确认的项目变量

以下选择会影响实现，但不改变本文的核心产品目标：

- 首批真实公司样本及 ATS 优先顺序；
- P0 必须支持的简历文件格式；
- 本地单用户模式还是最小 Token 身份模式；
- 模型、Embedding 服务及预算；
- 部署环境和定时任务运行方式；
- 原始简历、原始采集快照和运行日志的保留周期；
- 推荐评估集及首个 Top-K 质量目标。

如果仓库或任务没有给出答案，实现者应选择最小的可替换方案并记录假设；若选择会改变业务范围、公开接口、安全边界或产生明显外部成本，则应先向项目负责人确认。

## 10. P0 完成定义

P0 只有在以下端到端结果同时成立时才完成：

1. 能录入官方招聘源并完成至少一个真实 ATS 的完整采集闭环。
2. 能在三种有代表性的来源或采集方式上通过版本化样本验收。
3. 重复采集不重复入库，不完整采集不错误关闭历史岗位。
4. 能提交并修正用户画像，执行硬筛选、混合召回和结构化岗位评估。
5. 最终结果只组合真实岗位事实与有依据的匹配解释。
6. 用户与管理客户端可通过稳定 API 发起任务、查询状态并获取各自有权访问的数据。
7. 关键正常路径、失败路径和公共契约有自动化验证。
8. 系统可启动、可迁移、可观测，且不会在日志或接口中泄露敏感信息。

P0 完成后再按真实价值推进 P1，不以预留类、空接口或未验证配置代替已工作的能力。
