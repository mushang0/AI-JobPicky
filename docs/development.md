# JobPicky 开发协作约定

> 本文回答“开发任务如何理解、修改、验证和交付”。
> 产品范围与验收结果见 `requirements.md`；公共接口与跨模块约束见 `architecture.md`。
> 本文不重复维护业务字段、API 清单、表结构或算法设计。

## 1. 适用对象与目标

本文同时适用于项目维护者、Codex 和其他参与开发的 AI 或人工协作者。

协作目标是：

- 每次修改都有明确目的和完成证据；
- 多人或多任务并行时尽量不修改同一边界；
- 公共契约变化可见、可评审、可迁移；
- 实现细节保留弹性，不因流程规范产生无价值的样板代码；
- 主线在每个可交付节点都能启动、验证和继续演进。

这些是默认约定。仓库中的实际工具和命令优先于本文示例；如果项目规模尚不需要分支、PR、Worktree 或完整 CI，不应为了符合形式而创建它们。

## 2. 信息来源与冲突处理

不同信息只在各自职责内作为依据：

| 问题 | 依据 |
|---|---|
| 做什么、优先级和怎样验收 | `requirements.md` |
| 模块如何协作、哪些接口不能随意改变 | `architecture.md` |
| 如何拆任务、验证、评审和交付 | `development.md` |
| 当前实现和可运行命令 | 代码、测试、README 与项目配置 |
| 本次具体范围 | 最新的明确任务说明 |

处理冲突时：

1. 不修改需求来迁就已有代码，也不修改架构来掩盖实现偏差。
2. 先判断冲突属于产品、公共契约还是内部实现。
3. 内部实现冲突直接按当前基线修正。
4. 会改变产品行为或公共契约的冲突，先明确影响并按对应变更流程处理。
5. `design/爬虫架构设计.md` 和 `design/项目agent架构设计.md` 只用于理解背景，不覆盖三份基础文档。

## 3. 开发原则

- **先理解真实路径。** 修改前阅读相关代码、调用方、测试和配置，不根据文件名猜实现。
- **做最小的完整改动。** 优先完成一个可运行的纵向切片，不一次预建整套未来架构。
- **修根因。** 共享路径存在问题时，在共同入口修复并验证其他调用方。
- **保持边界，放松内部。** 公共 DTO、端口和 API 遵守 `architecture.md`；私有函数、目录和类按最简单方式组织。
- **显式失败。** 未支持、信息不足和外部依赖失败要返回真实状态，不用假数据、空实现或吞异常伪装完成。
- **不制造并行真相。** 同一字段、状态或规则只有一个权威实现；不要在多个模块复制相同业务判断。
- **保护现有工作。** 不覆盖无关改动，不使用破坏性 Git 操作清理不属于当前任务的内容。
- **验证与风险匹配。** 数据状态、身份、隐私和外部写入路径需要更强验证；局部纯函数不需要堆叠仪式。
- **按证据增加复杂度。** 新依赖、新抽象、队列、缓存和分布式组件必须解决当前可观察问题。

## 4. 一个任务的工作方式

### 4.1 理解

开始实现前，至少完成：

1. 阅读任务直接涉及的需求和公共契约。
2. 查看仓库级说明、依赖清单、现有测试和工作区状态。
3. 搜索相关定义与所有重要调用方。
4. 用一句话写清预期结果，并列出不在本次范围内的内容。
5. 找到能证明完成的最小验证方式。

如果任务只是解释、审查或诊断，只做读取和验证，不自行扩展为代码修改。

### 4.2 计划

满足任一情况时写一个短计划：

- 修改跨越多个模块；
- 涉及公共契约、迁移或外部服务；
- 存在两个以上需要按顺序验证的阶段；
- 任务较长，需要让其他协作者看到进度。

计划描述交付结果，不列出机械性的“打开文件、编辑文件”。保持一个步骤处于进行中，并在发现事实变化时更新计划。

小而明确的单文件修改可以直接完成，不必为了流程创建计划文档。

### 4.3 实现

- 沿现有代码风格和现有依赖实现。
- 优先复用仓库已有能力、标准库和平台原生特性。
- 只修改实现目标真正需要的文件。
- 不顺手做大范围格式化、重命名、依赖升级或无关重构。
- 外部输入在信任边界校验；内部不要重复做无意义的同一校验。
- 未完成的能力返回明确的“不支持”或失败状态，不提交会被误认为可用的占位实现。
- 注释解释非直观约束和取舍，不复述代码。

### 4.4 验证

先运行最接近改动的快速检查，再根据影响范围扩大：

```text
静态或 Schema 检查
→ 相关单元测试
→ 相关集成/契约测试
→ 必要的端到端或在线验证
```

不盲目假设测试命令。优先从 README、项目清单、CI 配置和现有脚本确认正确命令。

测试失败时区分：

- 本次修改引入的失败：修复后再交付；
- 已存在且与任务无关的失败：保留证据并在交付说明中指出；
- 因缺少外部依赖无法运行：执行仍可完成的离线检查，并明确未验证部分。

### 4.5 交付

交付说明保持简洁，至少包含：

- 实际完成的结果；
- 关键取舍或记录的假设；
- 已运行的验证及结果；
- 尚未验证、已知风险或真正的后续工作。

不要把阅读文件、调用工具等过程当成交付成果。

## 5. 如何处理不明确的问题

开发者应主动做低风险、可替换的判断，避免为私有实现细节频繁中断任务。

### 可以直接决定

- 私有文件、函数和类的组织；
- 满足现有契约的 ORM 或查询写法；
- 测试辅助代码和 fixture 组织；
- 不影响外部行为的重构；
- 已有技术栈内等价实现的选择。

选择最简单的方案，并让测试表达意图。

### 可以先假设并记录

- 可通过配置调整的批大小、超时和阈值；
- 尚无性能基线时的保守默认值；
- 可替换的内部库或适配层；
- 不影响数据兼容性的执行顺序。

假设应靠近配置、测试或交付说明，不另建长篇设计文档。

### 需要先确认或显式升级

- 需求优先级或用户行为存在相互冲突；
- 必须不兼容地修改公共 API、公共 DTO 或核心状态语义；
- 操作可能删除、覆盖或不可逆转换真实数据；
- 需要新的秘密凭据、付费服务、外部发布或高成本调用；
- 涉及访问控制绕过、隐私用途变化或其他安全边界；
- 两种选择会形成明显不同的产品，而任务和现有资料无法判断。

在等待决定前，可以完成不依赖该选择的安全部分，但不得假装阻塞部分已经完成。

## 6. 任务拆分与并行协作

按能力切片分工，不固定“开发者 A / 开发者 B”。在不同阶段，任何协作者都可以负责采集、岗位目录、画像、匹配或接口，只需明确当前任务所有权。

一个合适的任务通常：

- 有单一可观察结果；
- 输入、输出和验收方式明确；
- 修改范围集中；
- 能独立测试和回退；
- 不要求大量尚不存在的前置代码。

例如，“让某 ATS 的三页离线样本完整进入岗位目录且重复运行不新增”比“完成爬虫系统”更适合作为任务。

并行时遵守：

- 一个任务在同一时刻有一个主要负责人。
- 公共契约、迁移头、依赖清单、应用入口和 CI 是高冲突区域，修改前先同步。
- 能通过公开端口并行的模块不读取对方私有实现。
- 公共前置变更先形成小的独立交付，再让依赖任务同步。
- 显式使用多个 AI 子任务或 Worktree 时，只拆相互独立的范围，避免同时编辑同一文件。

不为了减少表面冲突复制公共 Schema 或临时建立第二套接口。

## 7. Git 与评审

项目进入 Git 后，默认做法是：

- 从最新可用主线开始短生命周期任务。
- 提交只包含当前目标需要的改动。
- 提交前查看 diff，确认没有秘密、生成物和无关文件。
- 不重写或丢弃其他人的未合并工作。
- 公共契约、迁移和安全边界变化至少由另一名协作者复核。

分支名和提交格式可以采用团队已有规范；没有规范时使用可读的 `feat/...`、`fix/...`、`docs/...` 及简短动词提交信息即可。

PR 或等价评审说明只需回答：

```text
完成了什么？
如何验证？
是否改变需求、公共契约或数据？
有什么已知风险或未完成项？
```

### 已验证的 GitHub 发布路径

下次需要从本地分支提交、推送、开 PR 并合并到 `main` 时，先从仓库根目录执行；路径不确定
时用 `git rev-parse --show-toplevel` 定位，避免在错误目录运行 Git 命令：

```bash
cd "$(git rev-parse --show-toplevel)"
git status -sb
git diff --check
uv run ruff check .
uv run ruff format --check .
uv run mypy src tests
uv run pytest
git add <本次改动文件>
git commit -m "fix: <简短描述>"
git push -u origin "$(git branch --show-current)"
gh pr create --base main --head "$(git branch --show-current)" \
  --title "<PR 标题>" --body-file /tmp/jobpicky-pr.md
gh pr checks <PR编号> --watch
gh pr merge <PR编号> --squash --delete-branch
git switch main
git pull --ff-only origin main
git branch -d <已合并分支>
git push origin --delete <已合并分支>
```

`gh auth status` 用于确认 GitHub 登录状态；`git branch -d` 删除本地分支，`git push
origin --delete` 删除远端分支。合并前先确认 PR 检查通过；如果 PR 已启用自动合并或仓库策略
不允许 CLI 合并，改在 GitHub 页面完成合并后再执行最后三条清理命令。不要用 `git add .`
带入不属于本次任务的生成物或其他人的改动。

Worktree 是并行任务的可选隔离手段，不是完成任务的要求。任务结束后再删除对应 Worktree 和分支，删除前确认改动已提交或不再需要。

## 8. 公共契约变更

公共契约范围由 `architecture.md` 确定。以下变化不能作为普通内部重构静默发生：

- 公共 DTO 字段或枚举的删除、改名、类型和语义变化；
- 跨模块端口输入输出变化；
- HTTP 路径、方法、状态码、权限或响应形状变化；
- 岗位身份、关闭保护、画像版本和用户隔离语义变化。

变更时按以下顺序处理：

1. 说明现有契约为何不能满足需求，以及是否有兼容方案。
2. 如果产品行为变化，先更新 `requirements.md`；否则不要改需求。
3. 更新 `architecture.md` 中唯一对应的契约定义。
4. 修改可执行 Schema、实现和契约测试。
5. 需要时提供向后兼容期或数据库迁移。
6. 让受影响模块的维护者评审并同步。

新增可选字段通常可以兼容演进；删除字段、收紧必填、改变枚举语义和改变路径通常需要版本化或迁移。不要同时在 `development.md` 复制字段定义。

## 9. 数据库与数据变更

只要存在持久化数据，就使用项目选定的迁移工具管理结构变化。

- 已共享或已部署的迁移不可原地改写。
- 一个迁移只表达一个连贯的数据变化。
- 结构迁移与业务回填分开，除非两者必须原子完成。
- 危险回填先验证受影响行数、空值、唯一冲突和回退方式。
- 岗位身份、状态关闭、画像版本和用户归属变化需要集成测试。
- 两个并行任务不要从同一迁移头各自创建互不知情的终点；先合并一个，另一个同步或使用工具支持的合并迁移。
- 不在测试和开发启动过程中自动执行不可逆生产数据操作。

如果还没有真实数据，可以保持首版 Schema 简单；不要为每个可能概念提前建表。

## 10. 测试策略

测试保护业务风险和公共边界，不追求每个函数都有一套重复测试。

| 改动类型 | 最小验证证据 |
|---|---|
| 纯规则、标准化、去重 | 针对正常值和关键边界的单元测试 |
| ATS 或网页采集 | 离线 HTML/JSON/HAR fixture；验证分页、详情、链接和空结果 |
| 岗位写入与状态同步 | 使用真实数据库语义的集成测试，尤其是不完整批次不关闭 |
| 画像或模型输出 | Schema 校验、缺失信息、幻觉字段和非法 `job_id` 测试 |
| 检索与融合 | 固定小数据集上的召回来源、去重和可复现测试 |
| 推荐编排 | 各阶段成功、可恢复失败、不可恢复失败和幂等测试 |
| HTTP API | 身份隔离、状态码、分页、错误形状与 OpenAPI 契约测试 |
| 公共契约 | 所有直接消费者相关测试，必要时完整测试 |
| 文档 | 职责去重、链接、术语和需求—契约—流程一致性检查 |

### 10.1 离线测试优先

普通开发和 CI 使用脱敏、版本化的离线响应。fixture 应尽量保留真实结构，但不包含 Cookie、Token、个人联系方式和不必要的大段受版权保护内容。

采集 fixture 至少覆盖实际遇到的：

- 多页和空页；
- 列表与详情分离；
- 多地点；
- 详情链接与投递链接不同；
- 字段缺失；
- 跳转或结构变化；
- 中途失败和异常数量下降。

### 10.2 在线测试显式执行

在线测试只在确有必要时手动或定时执行：

- 与普通 PR/提交检查分离；
- 限制频率、并发和总请求数；
- 记录来源、时间、结果与失败原因；
- 不把网络波动直接当作代码回归；
- 不使用登录绕过、验证码破解或真实用户秘密。

### 10.3 模型评估

模型测试不只检查“调用成功”。应使用小型人工标注样本验证：

- 明确匹配；
- 明确不匹配；
- 关键词相同但方向不同；
- 有相关技能但存在关键缺口；
- 硬条件冲突；
- 输入信息不足；
- 输出格式错误或返回未知岗位 ID。

确定性测试使用固定模型替身；真实模型评估单独记录模型、Prompt/配置版本、成本和结果，不让随机外部调用成为普通 CI 的必要条件。

## 11. 配置、秘密与日志

- 只提交无秘密的配置示例。
- 数据库凭据、模型密钥、Cookie、Token 和真实简历不进入仓库。
- 运行日志以 `request_id` 或 `run_id` 关联，记录阶段、耗时、数量和稳定错误码。
- 错误排查需要查看敏感原文时使用受控的临时方式，不提高全局日志级别长期记录。
- 第三方响应快照先脱敏，再进入 fixture 或调试附件。
- 新依赖先确认许可证、维护状态和是否确实优于已有能力。

## 12. 推荐交付顺序

以下顺序用于降低集成风险，不是固定人员分工或目录要求：

1. 建立可启动服务、配置、迁移、核心 DTO、健康检查和最小契约测试。
2. 用一个真实 ATS 样本打通“来源 → 采集 → 岗位目录 → 查询”的纵向闭环。
3. 用小型岗位集打通“画像 → 硬筛选 → 召回 → 评估 → 结果 API”的纵向闭环。
4. 补齐两条链路的运行记录、失败状态、幂等和事实重新组装。
5. 基于真实价值扩展其他 ATS、未知网站探索、定时任务和 P1 客户端能力。
6. 用版本化样本和指标决定下一轮质量优化，而不是先扩展架构。

每一步结束时都应有可演示结果，不等待所有模块完成后再首次集成。

## 13. 完成定义

一个任务只有在以下适用项成立时才算完成：

- 行为满足本次任务和 `requirements.md` 的对应验收；
- 公共输入输出符合 `architecture.md`；
- 没有混入无关修改或未经授权的范围扩张；
- 正常路径与关键失败路径有可重复验证证据；
- 相关测试通过，或已明确区分并记录无关的既有失败；
- 数据变化有迁移与安全验证；
- 配置、日志、fixture 和提交中没有秘密或敏感原文；
- 必要文档与代码在同一变更中保持一致；
- 交付说明列出实际验证和仍未覆盖的风险。

“代码已写”“接口返回占位数据”“测试以后再补”或“依赖未来模块才能运行”都不构成完成。
## 并行开发协作流程

1. 从 `requirements.md` 选择两个相对独立的小需求，创建递增编号的任务单。
2. 写明需求边界、分支和开发位置；两人从最新 `main` 创建分支，分别开发、测试并提交 PR。
3. 一个 PR 合并后，另一个分支先同步 `main`、解决冲突并重测，再合并。
4. 全部合并后，将任务单移入 `docs/tasks/archive/`，再创建下一轮任务单。

公共约束以 `architecture.md` 为准；修改公共契约前先同步。
