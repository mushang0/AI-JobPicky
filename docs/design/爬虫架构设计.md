# 岗位数据采集架构

## 一、目标

输入：

```text
公司名称 + 官方招聘链接
```

输出统一结构：

```json
{
  "company": "公司名称",
  "title": "岗位名称",
  "cities": ["深圳"],
  "jd": "岗位职责和任职要求",
  "job_detail_url": "岗位详情链接",
  "apply_url": "岗位直接投递链接"
}
```

---

## 二、核心方案

采用混合采集方案：

1. 先识别招聘链接属于飞书、北森、Moka等哪个ATS平台。
2. 已知平台使用对应平台适配器，多个公司复用同一套抓取逻辑。
3. 未知网站使用Playwright自动寻找“校园招聘”“查看职位”等入口，并监听网络请求，找到真实岗位接口。
4. 找到接口后，保存平台、接口地址、分页参数和字段映射，后续直接请求接口。
5. 无法找到接口的自建网站，再使用普通HTML解析或Crawl4AI兜底。
6. 定期检查抓取数量和字段完整率，规则失效时重新启动Playwright探索。

核心分工：

```text
平台适配器：负责日常稳定抓取
Playwright：负责第一次找路和规则失效修复
通用爬虫：负责未知网站兜底
```

---

## 三、抓取流程

```text
飞书表格提供公司名称和官方招聘链接
                ↓
跟随跳转，获取最终页面
                ↓
识别ATS平台
                ↓
已知平台：调用对应Adapter
未知平台：启动Playwright探索
                ↓
获取岗位列表接口
                ↓
处理分页，获取全部岗位
                ↓
获取岗位详情和投递链接
                ↓
转换成统一结构化字段
                ↓
校验、去重、写入岗位数据库
```

---

## 四、平台适配器怎么做

每个平台实现统一接口：

```text
detect：判断当前链接是否属于该平台
resolve：提取公司或租户参数
fetchList：获取全部岗位列表
fetchDetail：获取岗位JD和投递链接
normalize：转换成统一岗位结构
```

例如：

```text
FeishuAdapter
BeisenAdapter
MokaAdapter
GreenhouseAdapter
LeverAdapter
GenericApiAdapter
GenericHtmlAdapter
```

适配器内部主要处理：

```text
接口地址
请求参数
分页方式
岗位详情地址
字段映射
特殊加密或签名
```

新增公司时，通常只需要填写公司参数；只有出现新的ATS平台时，才需要新增适配器。

---

## 五、未知网站怎么处理

第一次遇到未知链接时：

1. Playwright打开页面。
2. 查找“校园招聘”“应届生招聘”“招聘职位”等按钮或链接。
3. 自动点击并处理跳转、新标签页和iframe。
4. 监听页面的XHR和Fetch请求。
5. 找出返回岗位列表JSON的接口。
6. 判断分页方式和岗位字段位置。
7. 保存为该公司的采集配置。

采集配置示例：

```json
{
  "platform": "generic-api",
  "list_api": "/api/jobs/search",
  "method": "POST",
  "items_path": "data.jobs",
  "title_path": "jobName",
  "city_path": "city",
  "jd_path": "description",
  "id_path": "jobId",
  "page_field": "page"
}
```

以后由`GenericApiAdapter`直接执行，不再重复操作浏览器。

## 六、测试集怎么建立

从真实飞书招聘数据中选取约40个公司链接：

```text
飞书招聘：5个
北森：5个
Moka：5个
其他ATS：5个
自建静态网站：5个
动态跳转网站：5个
iframe或多级入口网站：5个
空岗位、失效链接等异常情况：5个
```

每种情况都要包含：

```text
多页岗位
多城市岗位
JD需要单独请求
投递链接与详情链接不同
当前没有岗位
页面需要点击后才能看到岗位
```

---

## 七、测试方式

### 1. 离线测试

保存真实网站的：

```text
入口HTML
岗位列表JSON
岗位详情JSON
HAR网络请求记录
人工确认的预期结果
```

用于测试平台识别、分页和字段解析，避免每次测试都访问真实网站。

### 2. 在线测试

定期访问真实链接，验证：

```text
链接是否可访问
平台是否识别正确
是否抓到岗位
分页是否完整
核心字段是否为空
岗位数量是否异常
```

### 3. 人工黄金数据

每个网站人工确认几个岗位，记录：

```text
岗位名称
城市
JD
岗位详情链接
投递链接
```

将爬虫结果与人工结果进行对比。


未知自建网站单独统计，不和已支持ATS平台混在一起。

## 九、异常处理

如果某公司过去有100个岗位，本次只抓到2个：

```text
不能直接认为其他岗位已经下线
```

系统应该：

```text
标记本次抓取异常
→ 重试接口
→ 检查分页是否失效
→ 启动Playwright重新探索
→ 生成新的采集配置
→ 测试通过后替换旧配置
```

只有完整抓取成功后，才能更新岗位上下线状态。

---

## 十、最终实现原则

```text
已知ATS平台
→ 编写通用平台适配器

同平台不同公司
→ 只保存公司或租户参数

未知动态网站
→ Playwright发现真实接口

结构相似的自建网站
→ 配置型GenericApiAdapter

没有接口的网站
→ HTML解析或Crawl4AI兜底

规则失效
→ 自动检测并重新探索
```

最终核心架构是：

```text
平台识别器
+
ATS适配器库
+
公司采集配置库
+
Playwright接口发现器
+
通用网页解析器
+
真实网站测试集
```
