# JobPicky 实施计划

> 本文记录从空仓库到 P0 的交付顺序。产品范围以 `requirements.md` 为准，公共契约以 `architecture.md` 为准。

## 1. 架构结论

首版采用模块化单体：一个 FastAPI 部署单元、一个主业务数据库，长任务先通过可替换的执行器运行。逻辑模块是 `collection`、`catalog`、`profiles`、`matching`、`orchestration`、`api` 和 `infrastructure`。

模块边界遵循三条规则：

1. `catalog` 是岗位事实、身份和生命周期的唯一所有者。
2. `collection`、`profiles`、`matching` 只通过公共 DTO 与端口协作。
3. `api` 只调用应用服务，具体数据库、HTTP、模型和任务执行器由 `infrastructure` 适配。

## 2. 公共底座范围

当前阶段实现：

- 核心枚举、DTO、分页和错误响应；
- 采集、岗位目录、画像、评估与编排端口；
- 配置读取、请求 ID、统一异常处理、OpenAPI 和健康检查；
- 契约不变量与 API 的离线测试；
- Python 包、依赖、CI 和文档入口。

当前阶段不实现：

- 数据库表、迁移和 Repository；
- ATS、Playwright 或 HTML 采集器；
- 简历文件解析、Embedding、LLM 与 LangGraph；
- Worker、调度器、认证系统和未落地的业务 API。

这些能力需要真实样本或明确的首期选型，提前创建空实现只会形成第二套不可信契约。

## 3. 交付阶段

### 阶段 0：公共底座

交付可启动服务、公共契约、端口、健康检查、统一错误与测试基线。完成标准是代码可安装、OpenAPI 可生成、契约测试和 CI 通过。

### 阶段 1：首个采集纵向切片

选择一个真实 ATS 离线样本，加入 PostgreSQL、迁移、招聘源、采集运行和岗位目录。打通“来源 → 采集 → 幂等写入 → 岗位查询”，重点验证重复采集与不完整批次保护。

### 阶段 2：首个推荐纵向切片

确定首期简历输入格式、身份方式、模型和 Embedding 服务。打通“画像版本 → 硬筛选 → 双路召回 → 结构化评估 → 事实重组 → 结果查询”。

### 阶段 3：运行保障

补齐长任务执行器、幂等键、有限重试、正式运行记录、敏感日志控制和服务重启后的安全重跑。

### 阶段 4：扩展与评估

按真实价值增加另外两种来源或采集方式，建立版本化采集样本和推荐评估集，再用指标决定是否引入浏览器探索、LangGraph、独立 Worker 或更复杂检索。

## 4. 开始下一阶段前的输入

- 首个真实公司与 ATS 样本；
- P0 简历文件格式；
- 本地单用户或最小 Token 身份模式；
- PostgreSQL、Embedding 与模型服务的运行方式和预算；
- 原始简历、采集快照与日志保留周期。
