# JobPicky 实施计划

> 本文记录当前从公共契约冻结到 P0 纵向闭环的交付顺序。
> 产品范围与验收结果以 `requirements.md` 为准；用户 API 的确认契约以 `api-requirements.md` 为准；
> 跨模块所有权和端口以 `architecture.md` 为准。

## 1. 当前阶段：前端 API 公共契约同步

当前先完成可执行边界，不提前实现业务路径：

- `docs/api-requirements.md` 纳入版本管理并单独提交；
- 同步需求、架构和本实施计划，消除旧画像、旧推荐和旧路径语义；
- 增加岗位列表/详情/筛选选项、认证用户、积分、当前画像、推荐卡片、任务进度和收藏状态 DTO；
- 保留 `JobFact`、`Candidate`、`MatchAssessment`、`RecommendationItem` 等内部匹配 DTO，前端响应使用独立 View；
- 扩充稳定错误码、中文用户提示、鉴权/积分/收藏/画像/推荐最小端口；
- 增加岗位池、分页、推荐、积分、JWT、Cookie、CORS 和限流配置，并提供无秘密 `.env.example`；
- 通过契约测试和 OpenAPI 生成/校验检查字段、范围、序列化、错误形状和当前路由边界。

本阶段不创建返回假数据的业务路由，不实现认证、积分、收藏或推荐交互的空 Repository，不修改已发布迁移来
掩盖尚未交付的持久化能力。当前应用只保留真实健康检查和已有可运行路径。

## 2. 公共契约不变量

1. 岗位事实只有 `catalog` 负责；`JobListItem`、`JobDetailView`、收藏岗位和推荐卡片都由 `JobFact` 重组。
2. 推荐内部评估 DTO 与前端卡片 DTO 不共用响应结构；内部 `retrieval`、完整 JD、`fact_version`、Embedding
   和来源秘密不进入前端卡片。
3. 一个用户只有一个逻辑当前画像；`PUT /user/profiles/current` 用 `base_version` 和幂等键创建新快照，
   内容无变化不递增版本。
4. 推荐任务自动读取创建时的当前画像版本；任务最多 50 个候选，状态进度必须来自真实阶段，不返回预计剩余时间。
5. 用户身份从认证上下文获得，不信任请求体中的 `user_id`、画像 ID 或角色；用户资源查询必须带用户边界。
6. 积分扣费、退款和推荐任务创建按业务边界幂等；错误码使用稳定英文机器码，用户 `message` 使用中文。
7. 未实现能力没有占位接口；OpenAPI 只列出真实已注册路由，契约 DTO 的 schema 通过独立模型校验冻结。

## 3. 交付阶段

### 阶段 0：公共底座（当前）

交付文档、Pydantic Schema、端口、配置、错误映射、OpenAPI/契约测试和可启动健康检查。完成标准是：新 API
需求、`requirements.md`、`architecture.md`、可执行 Schema 与错误码没有互相矛盾，且主测试通过。

### 阶段 1：岗位池与画像纵向切片

在新增真实持久化迁移后实现岗位池公开预览、登录后查询、筛选选项、统一岗位详情、认证账户和当前画像保存。
该阶段验证匿名/登录边界、规范化筛选、画像版本冲突、会话轮换和用户隔离；未知岗位字段继续遵循“未知保留”。

### 阶段 2：推荐与积分纵向切片

实现推荐任务创建、原子扣费、当前画像绑定、硬筛选、关键词/语义召回、最多 50 个候选、结构化评估、事实重组、
任务进度、退款和推荐结果持久化。只有 `matched=true` 的结果进入正式推荐；失败退款和重复请求都必须幂等。

### 阶段 3：收藏与推荐交互

实现 `user_id + job_id` 唯一收藏、收藏列表、推荐反馈和软删除推荐。验证岗位池、详情、推荐卡片和收藏列表共享
同一收藏状态；软删除只影响“全部推荐”，不破坏任务历史和后续推荐去重。

### 阶段 4：采集与运行保障

在公共用户契约稳定后继续完成真实 ATS、采集运行、岗位目录写入、迁移、恢复、有限重试和敏感日志控制。任何
不完整采集都不能关闭历史岗位；未经验证的未知来源配置不能直接启用。

## 4. 每阶段验证顺序

```text
Pydantic 字段/范围/序列化
→ 端口签名与用户上下文
→ OpenAPI schema 与真实路由边界
→ 离线契约/单元测试
→ 相关数据库集成测试
→ 完整 ruff、format、pytest（必要时 mypy）
```

涉及秘密、真实简历、Cookie、Token、真实网站响应或远端发布的操作必须单独受控；本阶段不需要这些外部状态。
