# 用户体验与推荐质量改进需求与实现建议

> 状态：待实现建议
> 依据：最新前端反馈与补充意见；公共边界仍以 `requirements.md`、`architecture.md`、`api-requirements.md` 和 `development.md` 为准。
>
> 本文只说明要解决的问题、产品行为和实现方向，不指定具体组件、函数、表结构或页面尺寸。

## 1. 目标

本轮改进聚焦三件事：

1. 页面根据用户是否有画像、是否有推荐任务和是否有推荐结果展示正确的下一步。
2. 面向用户重写页面、进度和错误文案，隐藏实现细节，让用户知道当前能做什么、正在发生什么以及失败后怎么办。
3. 改善岗位匹配的输入和判断依据，减少通用技术词造成的方向误匹配，同时保留模型对最终语义匹配结果的判断权。

不以新增后端业务能力或重做整体架构为目标。优先复用现有画像保存、推荐任务、岗位事实和推荐结果接口。

## 2. 需求范围

### 2.1 画像创建与查看

首次创建画像改为分步引导。每一步只要求用户完成一个明确决策，顺序覆盖目标岗位、城市、招聘类型、学历与毕业时间、技能、项目或经历、薪资/排除项/其他要求，最后确认保存。

引导过程中的未完成内容可以暂存在前端，完成后再调用现有画像保存能力。首版不因为分步交互新增画像表、草稿接口或新的画像持久化模型。

返回上一步时必须保留已经填写的内容；各字段是否必填或允许跳过沿用现有画像契约，不因改成分步流程而擅自收紧或放宽画像语义。创建和编辑应使用一致的步骤和字段规则。跨页面刷新恢复未完成草稿不是本轮必须能力，除非后续单独确认。

已有画像时进入画像摘要，而不是继续展示长编辑表单。摘要至少能让用户理解目标岗位、城市、招聘类型、学历与毕业时间、技能、经历、薪资、排除项和其他要求，并提供两个主要动作：

- 开始推荐；
- 修改画像。

点击修改后重新进入编辑流程；保存成功后回到摘要。服务端的 `version`、`base_version`、画像 ID、幂等和历史绑定语义继续保留，但版本号、画像 ID、并发控制术语和“版本 X”不作为普通用户文案。

### 2.2 根据用户状态展示推荐页面

“全部推荐”和“推荐任务”不能只根据结果数组是否为空决定空状态。页面应结合当前画像、推荐任务和推荐结果判断状态；加载或接口失败时也不能误判成“没有画像”。可以通过并行查询或登录后的轻量画像状态缓存实现，不新增专门的后端状态接口。

| 用户状态 | 主要展示与动作 |
|---|---|
| 没有画像 | 引导创建求职画像 |
| 有画像、没有推荐任务 | 引导开始第一次推荐 |
| 有任务且正在运行 | 展示正在查找岗位，并可进入任务详情 |
| 有成功任务但没有匹配结果 | 说明本次没有找到合适岗位，提供调整画像或重新推荐 |
| 有推荐结果 | 展示推荐列表 |
| 任务失败 | 展示脱敏的失败原因、退款/积分状态和可执行的重试或返回动作 |

推荐任务页采用统一结构：中央只保留一个当前最重要的主操作，历史任务在其下方展示。没有画像时主操作是创建画像；有画像时主操作是开始推荐；有历史任务时仍保留开始新推荐入口，但不再在右上角重复放置“新建推荐”。没有画像时不能直接创建推荐，页面应在用户动作前后都给出明确引导。

### 2.3 用户可见文案重写

检查并重写以下页面及其空状态、加载状态和错误状态：

- 我的求职画像；
- 全部推荐；
- 推荐任务列表；
- 新建推荐；
- 推荐任务运行页；
- 岗位池；
- 通用错误、失败和无结果状态。

文案应优先回答“这里能做什么”“下一步做什么”“系统正在做什么”“失败后怎么办”。删除或改写结构化求职档案、确定性筛选、岗位召回、AI 评估、接口步骤、轮询频率、当前版本、任务编号、可追溯记录、公开访问限制和筛选配置等内部语言。

代表性方向如下，最终文案不需要在本计划中一次性穷举：

| 内部表达 | 用户化方向 |
|---|---|
| 这是推荐系统使用的结构化求职档案 | 告诉我们你想找什么样的工作 |
| 推荐任务只读取已保存的版本 | 保存后，我们会根据这些信息为你寻找岗位 |
| 岗位召回与 AI 评估 | 这些信息能帮助我们判断你和岗位是否合适 |
| 每次推荐，都留下一条可追溯记录 | 查看每一次岗位查找的结果 |
| 任务编号、每 2 秒更新状态 | 普通页面隐藏；只在故障排查需要时保留内部信息 |

内部运行标识、阶段、错误码和详细日志仍可用于诊断，但不应出现在普通用户界面或公开错误信息中。

### 2.4 推荐结果、发布日期和来源

“全部推荐”默认按匹配度从高到低展示，保留“最新推荐”作为可选排序。前后端默认值应保持一致，同分时使用稳定的次级顺序，避免翻页或刷新时结果无故跳动。匹配分可以继续用于排序和展示，但不能作为固定通过阈值，也不能单独决定岗位是否进入推荐。

“全部推荐”的排序规则与单次推荐任务详情分开：全部推荐按用户选择的全局排序展示；单次任务结果默认保留该次任务形成的原始顺序，不因全局列表排序而改变历史结果的阅读顺序。

推荐卡片不再突出“推荐时间 · 发现时间”。卡片优先表达投递时效：

- 有明确未来截止时间时显示截止日期；
- 没有明确截止时间时显示“建议尽快投递”；
- 已截止或岗位当前已关闭时显示相应状态，并降低卡片权重或禁用投递动作。

推荐理由、标题、公司等历史判断内容继续使用推荐时保存的快照；截止日期和当前开放状态优先读取最新岗位事实，必要时再回退到快照。`first_seen_at` 与推荐时间可以继续作为内部或兼容字段保留，但不再被当作用户关心的发布日期或卡片主信息。

岗位详情页应在数据已知时显示真实的发布日期和投递截止日期。岗位池的主日期筛选改为“发布日期”，数据来源是岗位事实中的 `published_at`，可提供最近 3 天、最近 7 天、最近 30 天等用户可理解的时间范围，并能表达“发布日期未注明”。不能用执行扫描时间 `first_seen_at` 代替发布日期，也不能为缺失发布日期的岗位猜造日期；缺失日期可以隐藏或明确标注未知，但不能伪造。

现有来源标识和 `source_id` 接口继续保留以兼容管理和排查，但普通筛选不应把公司名称当作来源展示。

来源显示应来自来源目录的规范化渠道：已知招聘平台显示平台名，自建招聘官网显示“企业官网”，政府或公共招聘公告、微信公众号等使用对应渠道名称；未知来源不能退回为公司名称。来源若仍对普通用户有价值，可放入次级筛选或“更多筛选”，不作为主操作入口。

如推荐卡片缺少当前岗位的 `deadline_at`、`published_at` 或 `status`，可增加兼容的可选响应字段或在查询层组合现有岗位事实；不删除现有客户端仍可能使用的字段。若发布日期筛选需要新增查询能力，也应以可兼容的方式同步更新 API 契约、OpenAPI 和测试。

### 2.5 运行进度与搜索体验

进度的完成语义必须来自服务端真实阶段：只有任务成功完成才显示 100%，失败不能伪装成完成。前端将真实进度与视觉活动状态分开处理：数值在阶段变化时平滑过渡，长时间等待时可以在当前阶段范围内保持轻微活动，但不能跨阶段或提前完成。

运行页隐藏轮询频率、任务编号和接口字段，使用面向用户的阶段描述，例如“正在理解你的求职方向”“正在寻找相关岗位”“正在比较你的经历和岗位要求”“正在整理推荐结果”。

搜索动画以现有前端能力为主，用 CSS/SVG 表达画像信息、岗位搜索和结果收集；不引入 Canvas、复杂 3D 或新的重型动画依赖。画像词条只取少量、非敏感的真实画像信息，不展示完整简历或内部数据。必须支持 `prefers-reduced-motion`，减少动画时显示静态状态和文字信息。

动画需要适配移动端并控制性能，不能因为装饰效果影响任务页可用性。后端没有逐个岗位事件时，不得伪造“已找到 N 个岗位”、逐张卡片被分析或推荐数量增长；此时只表现为正在搜索或分析，真实数量仍以服务端返回为准。

## 3. 推荐判断改进边界

### 3.1 保留确定性过滤与模型判断的分工

确定性逻辑继续负责开放状态、城市、招聘类型、学历、届次、薪资下限和明确排除项等硬条件。信息缺失仍然是未知，不应被擅自转换为不符合；学历比较遵循最低要求语义，例如硕士满足本科要求。

未通过硬筛选的岗位不能进入最终评估，模型也不能把它重新带回推荐结果；但已经通过硬筛选的岗位，即使存在语义差距，也不能被后端按固定规则自动否决。

客观条件的结论应以简洁、结构化的方式提供给评估模型，例如“学历满足”“城市满足”“招聘类型满足”或“信息未知”。模型不能把已经确认满足的条件写成不匹配或能力缺口，也不能把 `UNKNOWN` 自行解释成不符合。若模型输出与这些客观事实明显矛盾，可以拒绝该次输出或请求模型修正，但不能由后端擅自改写模型最终的推荐结论。

召回只负责找到候选岗位。`retrieval_score`、`keyword_score` 和 `semantic_score` 是候选发现依据，不是最终适合度证据。优先不把这些分数传给最终评估模型；若因兼容原因保留，必须明确告知模型它们不能作为推荐理由或匹配结论。

最终是否推荐仍由模型综合判断并输出 `matched`。后端的职责是校验结构、候选岗位 ID、事实引用、硬条件一致性和敏感边界，再用岗位目录事实组装结果；后端不通过分数、某个缺口或某个枚举值重新推导 `matched`。模型可以判断“有差距但值得推荐”，也可以判断“核心方向差异导致不推荐”。

### 3.2 调整模型判断顺序和规则

评估提示应要求模型按以下顺序思考：

1. 识别岗位核心方向；
2. 识别岗位核心职责；
3. 判断用户是否有直接对应经历；
4. 区分通用能力与可迁移能力；
5. 判断差距属于次要、可补足，还是会影响岗位核心工作；
6. 综合以上信息决定是否推荐。

提示中明确说明：共享 Python、PyTorch、模型部署、推理优化等通用技术不等于岗位方向一致；视觉模型经历不能自动等同于 NLP 经历；可迁移能力可以形成推荐优势，但不能被写成用户已经做过不存在的领域工作；岗位允许存在差距，差距的存在本身不能自动导致不推荐，关键在于对核心职责的影响和迁移基础。

### 3.3 让证据表达对应关系

当前普通字符串 evidence 容易退化成重复用户经历。建议在内部模型输出中增加更清晰的“岗位要求—用户证据—结论”对应关系，至少能够表达：岗位要求、候选人证据、匹配关系、重要性、解释。

匹配关系可以区分直接匹配、可迁移、部分匹配、差距和未知；重要性可以区分核心、优先要求和可选项。这些结构用于帮助模型形成判断、校验事实和生成更好的前端投影，但不能简单规定某个枚举值必然等于 `matched=false`。

前端继续展示自然语言的推荐理由、匹配优势、需要关注的差距和判断依据，不直接暴露内部枚举、召回分或完整评估输入。

### 3.4 不新增固定匹配阈值和专门评估集

本轮不通过召回分或 `match_score` 设置固定推荐阈值，不以“存在 critical gap”一类规则机械否决岗位，也不改为由后端代替模型决定最终是否推荐。

本轮不建立一套额外的 30～50 组人工标注推荐质量数据集。仍应保留最小的结构化输出、硬条件一致性、事实引用和已知错误案例验证，避免学历判断和方向误匹配问题在修改后立即回归；这不扩展为独立的模型评估项目。

## 4. 实现建议

按风险和用户收益分批推进：

1. **先修状态和明显逻辑**：统一画像/任务/结果状态判断，修正无画像阻断、空状态主操作、默认排序、截止日期和发布日期筛选语义，规范来源显示。
2. **再重做画像交互**：实现引导创建、画像摘要、独立编辑和保存后的页面切换；复用现有保存接口与版本控制，不提前增加后端草稿能力。
3. **随后改善评估输入**：收紧最终评估输入，优先移除召回分；完善提示词判断顺序和证据对应结构；保留模型 `matched` 决策，并加强结构/事实/硬条件校验。
4. **最后完善运行体验**：平滑真实进度，加入轻量搜索与收集动画、移动端适配和减少动画模式。动画不能掩盖失败、未知或尚未完成的真实状态。

如果内部评估输出或推荐卡片响应发生变化，先判断是否属于公共契约变更。新增可选字段通常可以兼容，但仍需同步 `api-requirements.md`、`architecture.md`、可执行 Schema、OpenAPI 和受影响测试；不要为了前端展示复制一套独立岗位事实或推荐结果来源。

## 5. 明确不在本轮范围内

- 不新增画像草稿接口、数据库表、PDF 简历解析或 AI 对话完善画像入口。
- 不删除或改写服务端画像版本、并发控制、任务幂等和岗位事实追溯语义；只改变用户呈现方式。
- 不以固定匹配分、召回分、`critical_gap` 或单个证据枚举替代模型的最终判断。
- 不建立独立的大型推荐质量测试集，不把本轮扩展为模型选型或训练项目。
- 不把 `first_seen_at` 解释成发布日期，不删除现有来源 ID/来源接口，不让公司名继续伪装成来源渠道。
- 不引入 Canvas、复杂 3D、重型动画库或微服务等与本轮目标无关的基础设施。
- 不更换整体前端框架，不引入 LangGraph、多 Agent 或其他新的工作流架构，不训练或微调模型。
- 不大范围重构与本轮问题无关的认证、积分、采集和数据库模块。
- 不向用户暴露任务编号、轮询频率、内部进度字段、召回分、模型提示词、完整简历或原始错误堆栈。

## 6. 验收重点

- 首次进入画像页是分步创建；已有画像进入摘要，保存后回到摘要且不显示版本号。
- 有画像但无推荐时不再提示创建画像；无画像时不能直接开始推荐，推荐任务页只有一个明确的主操作。
- 分步画像返回上一步时已填写内容不丢失；保存后进入摘要且不显示版本号。
- 全部推荐默认按匹配度降序，排序仍可切换到最新推荐，同分顺序稳定；单次任务结果不被全局排序改写。
- 推荐卡片和岗位详情页使用真实截止日期、发布日期和岗位状态；无截止日期时给出“建议尽快投递”，无发布日期时不伪造，已截止或关闭岗位不会继续引导投递；岗位池的日期筛选使用发布日期。
- 普通用户看不到结构化档案、确定性筛选、召回、轮询、版本、任务编号、公开访问限制等内部表述，错误状态包含可执行的下一步。
- 硕士不会因为岗位最低学历为本科而被误判为不符合；视觉模型经历不会仅凭通用技术词被当作 NLP 直接经历。
- 评估模型能够看到客观条件的满足/未知结论；满足项不会被写成缺口，未知项不会被擅自判定为不符合，事实矛盾会进入失败或修正流程而不是被后端静默改写。
- 匹配依据能够同时表达岗位要求与用户证据，差距可以存在但不会被规则机械地视为不推荐；最终 `matched` 仍来自模型综合判断。
- 评估模型默认不接收召回分；即使保留，也不会把召回分当作最终匹配证据。
- 长时间模型调用时进度持续表现为正在工作，但不会提前显示完成或伪造逐岗计数；移动端和减少动画模式下仍能理解当前状态。
- 最小自动化验证覆盖学历逻辑、画像状态空页面、默认排序、日期字段和来源规范化，但不扩展为人工标注推荐评估集。
