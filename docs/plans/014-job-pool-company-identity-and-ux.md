## 1. 已确认的产品决定

### 1.1 公司卡片代表真实公司

公司卡片不再代表一条 Feishu 记录，而代表一个真实公司。

现有 `company_group_key` 主要使用 `feishu_record_id` 或表格行号，因此同一公司在多条 Feishu 记录中会拆成多个公司卡片。新的公司身份计算顺序为：

1. 已有公司画像匹配成功时，复用 `metadata.company_group` 作为规范公司身份。
2. 没有公司画像时，使用规范化后的公司名称作为兜底。
3. Feishu 记录 ID、表格行号和来源 URL 只保留为来源证据，不再决定公司卡片归属。

当前已有的公司画像已经能覆盖百度：`百度` 和 `百度移动生态事业群` 的 490 条岗位都被标记为 `company_group=baidu`，因此不需要新增公司主数据表或模糊匹配系统。

### 1.2 公司卡片显示原始 Feishu 批次

当前数据库中的 `batch` 和 `batch_tokens` 就是从 Feishu `批次` 字段保存下来的原始值，15,015 条岗位全部有这两个字段。

公司卡片左上角直接展示公司所有岗位去重后的批次标签，例如 `秋招专场`、`实习`、`秋招提前批`。用户界面可以继续把这组标签作为“招聘类型”展示，但内部必须注明数据源是原始 `batch_tokens`，不再额外设计一套推导规则。

`recruitment_type` 是另一套规范化字段，目前只有 13,554 条岗位有值；同一个 `秋招专场` 在数据中同时出现过 `校招` 和 `社招`，而 `实习` 也有一部分岗位没有规范化招聘类型。因此公司卡片不应使用 `recruitment_type` 替代原始批次。

### 1.3 公司性质展示原始事实，筛选仍可使用规范值

Feishu 原始企业性质已经进入岗位数据。当前 2,541 条岗位的原始值是 `央国企`，但规范化函数没有覆盖该值，所以数据库中的 `company_nature` 被写成了空值，前端才显示“公司性质待确认”。

计划将“展示值”和“筛选值”分开：

- 公司卡片优先显示 Feishu 原始企业性质；
- 筛选继续使用规范化值；
- 原始值无法规范化时也不能丢失或显示“待确认”；
- 公司内存在多个性质时展示去重后的多个值，不使用 `min(company_nature)` 随机挑选一个。

| 有原始 `batch` | 15,015 | 100% 覆盖 |

| 有规范化 `recruitment_type` | 13,554 | 不是原始批次的替代字段 |

### 2.1 百度重复证据（修改前）

当前库中百度相关岗位共 490 条：

- `百度` 公司名下 489 条岗位；
- 只有 163 个不同的 `source_job_id`；
- 这 163 个岗位全部各出现 3 次；
- 3 份重复记录的 `detail_url` 相同，但 `source_id` 不同；
- 这 489 条被拆成 3 个不同的 Feishu 公司组；
- 因此百度至少有 326 条重复岗位记录，不是视觉重复。

全库范围内还发现：

- 1,573 组 `source_job_id` 重复，至少多出 2,737 条记录；
- 按“同公司 + `source_job_id`”收窄后仍有 424 组、至少 587 条重复记录；
- 使用公司、标题、城市、招聘类型、学历、薪资和完整描述组成的保守事实指纹，发现 519 组、至少 1,423 条重复候选。

最后一个数字是候选数，不直接等于可以删除的数量；同名岗位在不同批次、城市或招聘范围下可能是合法的不同岗位，必须先经过强身份和事实一致性校验。

### 2.2 已确认的根因

现有岗位身份包含原始 `source_id`。而 `source_id_for_entry()` 会把来源 URL 的查询参数纳入来源 ID，因此百度的不同招聘页面参数会得到不同来源。随后 `_identity_key()` 使用 `source_id + source_job_id` 生成岗位身份，同一个百度外部岗位 ID 就被当成多个岗位。

公司身份则优先使用 `feishu_record_id`，所以同一真实公司下的多条 Feishu 记录必然形成多个公司组。

## 3. 本轮需求范围

### 3.1 岗位池和公司视图

1. 默认只显示搜索框；点击或聚焦搜索框后展开筛选。
2. 展开筛选后，右侧显示同宽同高的“清除筛选”和“应用筛选”。
3. 点击其他区域或按 Escape 关闭筛选；未应用的草稿条件不改变当前结果。
4. 详情返回时保留列表 URL、搜索条件、筛选条件、公司/岗位视图、页码和滚动位置。
5. 公司卡片代表真实公司，合并同一公司在不同 Feishu 记录和来源中的岗位。
6. 公司卡片左上角显示去重后的原始 Feishu 批次标签，不再显示无意义的“公司”。
7. 公司卡片使用 Feishu 企业性质展示值，不再因为规范化失败显示“公司性质待确认”。
8. 岗位去重同时覆盖跨 Feishu 记录、跨来源 URL 和同一来源重复采集。

### 3.2 推荐页面

1. “开始推荐”和“历史推荐”分成两个视觉区块。
2. 新建推荐页减少说明文字和装饰，突出补充要求、消耗信息和唯一主按钮。
3. 推荐运行页只保留一个主状态、一个进度条和一个当前活动说明。
4. 删除重复的“运行中”、重复放大镜和无实际依据的精确耗时文案。
5. 进度以服务端真实状态为准，前端只做短距离平滑过渡。
6. 搜索/匹配过程可以轮换展示真实流程文案，但不能伪造逐岗位事件或结果数量。

## 4. 实现方案

### 阶段 A：修正岗位身份与公司身份

#### A1. 规范公司身份

复用 `src/jobpicky/collection/company_profiles.py`，在岗位写入时计算规范公司组：

```text
已有 company_group → company:<group_id>
否则             → name:<规范化公司名>
```

`feishu_record_id`、`table_row_number`、来源 URL 等信息继续保留在 metadata，供来源追溯和后续采集使用。

不新增公司主数据表、不做模糊字符串相似度合并、不把公司名称交给模型判断。已有公司画像覆盖的别名通过现有配置维护；没有画像的公司先按规范化名称精确聚合。

#### A2. 修正岗位身份

不全局删除 `source_id`，避免不同平台或不同公司的相同外部 ID 被错误合并。身份范围按以下顺序选择：

1. 已知解析器/平台和规范公司组组成来源范围，再结合稳定 `source_job_id`；
2. 没有稳定外部 ID 时，继续使用规范化详情 URL；
3. 最后才使用强事实指纹，并要求公司、标题、城市、招聘类型、学历、薪资和描述等字段满足一致性。

对百度而言，同一 `company_group=baidu`、同一解析器和同一 `source_job_id` 应得到一个岗位身份，即使来自不同 Feishu 记录或不同列表 URL。

保留来源记录的并集，避免合并时丢失 Feishu 记录 ID、批次和来源证据。不要用一次不完整采集触发历史岗位关闭。

#### A3. 公司列表契约

继续复用 `CompanyListItem` 和 `company_group_id` 路由，但显式改变其语义：`group_id` 表示规范真实公司，不再表示单条 Feishu 记录。需要同步更新：

- `docs/architecture.md`；
- `docs/api-requirements.md`；
- 后端 DTO、OpenAPI 和前端类型；
- 公司列表、公司筛选和公司详情测试。

为兼容已有链接，实施时先评估是否需要把旧的 `feishu:<record_id>` 查询参数转换到新的规范公司组；不能无提示地让历史链接全部失效。

### 阶段 B：公司卡片字段和岗位池查询

#### B1. 批次标签

公司查询使用现有 `job.batch_tokens`，在查询层对同一规范公司做去重聚合，新增一个最小的公司响应字段，例如 `batches`。不新建“公司招聘类型”表，不重新解析 Feishu。

排序使用固定顺序：保留原始值，同时可将包含 `校招`、`社招`、`实习` 的值放在前面；不能为了排序改变标签原文。公司卡片显示有限数量，完整值通过详情或辅助文本承载，避免卡片被长批次撑高。

#### B2. 企业性质

后端保留规范化字段用于筛选，同时增加或投影一个展示值：

- 优先读取 Feishu 原始企业性质；
- 原始值缺失时才显示“未注明”；
- 不再把“规范化函数返回空值”解释为“待确认”。

现有 `央国企` 需要补充明确的规范化规则和测试；是否映射为统一的筛选枚举，应与展示原文分开处理。

公司聚合不能继续用 `min(company_nature)`。应收集公司岗位中所有非空展示值，去重后返回单值或多值。

### 阶段 C：岗位池交互和返回状态

#### C1. 筛选

- 桌面和移动端统一使用同一套展开/关闭状态。
- 搜索输入获得焦点或被点击时展开筛选。
- 点击面板、下拉菜单和按钮时不触发外部关闭。
- 点击页面其他区域或按 Escape 关闭。
- 草稿条件只在“应用筛选”后写入 URL。
- “清除筛选”清空 URL 条件并关闭面板。
- 两个操作按钮使用同一 `min-height`、`min-width`、padding 和对齐规则。
- 补上已有 API 支持但前端缺失的招聘类型筛选入口，若产品决定筛选使用规范类型，则不影响公司卡片使用原始批次。

#### C2. 返回岗位池

不引入全局状态库。使用浏览器 History 作为首选，使用 `location.state` 或受限的 `returnTo` 记录来源列表，使用 `sessionStorage` 按列表 URL 保存滚动位置。

以下入口统一接入：岗位卡片、公司卡片进入岗位列表、推荐卡片、收藏岗位和推荐任务结果。

### 阶段 D：推荐页面视觉和状态

#### D1. 推荐记录

保留现有路由和接口，只重新组织页面层级：

```text
推荐记录
  [开始新的推荐]

历史推荐
  [推荐记录列表]
```

“开始新的推荐”是独立操作区；历史记录有自己的标题和间距。

#### D2. 新建推荐

保留当前双栏结构，但压缩左侧说明：

- 标题只出现一次；
- 一句话说明用途；
- 流程压缩为“读取画像 / 筛选岗位 / 生成结果”；
- 去掉突兀的大图标方块；
- 右侧只保留补充要求、消耗信息、画像状态和主按钮。

不新增组件库，不替换现有颜色、圆角和 Phosphor 图标体系。

#### D3. 推荐运行页

运行状态只保留一处，建议使用“正在生成推荐”作为主标题；进度卡片只展示当前步骤、百分比和一条进度条。

进度规则：

- 服务端百分比是唯一事实；
- 前端只在相邻服务端进度之间平滑过渡；
- 长时间等待时保持真实进度，使用轻量 shimmer 或“正在处理”表达活动；
- 成功才显示 100%；失败不能伪装完成；
- 没有真实 ETA 时删除“通常还需 2–6 分钟”等精确时间。

活动说明每次只展示一条，例如“读取求职画像”“筛选开放岗位”“比较岗位要求”“整理推荐结果”。这些文案必须对应真实阶段，不展示伪造的逐岗位搜索事件。

## 5. 历史数据处理和安全边界

### 5.1 先报告，后合并

实现前先提供只读重复报告，至少包含：

- 规范岗位身份碰撞组；
- 同一外部 ID 的来源范围和详情 URL；
- 公司组变化前后数量；
- 合并候选的事实差异；
- 收藏、推荐、岗位引用数量；
- 将被保留和被合并记录的明确 ID。

报告通过后再做一次性回填或迁移。不在应用启动、普通采集或用户访问岗位池时自动删除历史记录。

### 5.2 合并规则

只有以下情况允许自动合并：

- 同一规范来源范围；
- 同一稳定外部岗位 ID，且详情 URL 或强事实一致；
- 或无外部 ID 时，强事实指纹完全一致。

合并时保留最新完整岗位事实、最早/最近看到时间、所有来源记录和批次标签；保留外键引用，必要时先迁移 `saved_job`、`recommendation` 等引用再处理旧岗位记录。

本轮报告中的可合并候选没有 `saved_job` 引用；全库当前有 46 条 `recommendation` 记录，其中 1 条落在一个事实/URL 冲突的未合并候选组内。部署环境不能据此假设没有引用，必须在回填前检查。

### 5.3 不完整采集保护

当前 Feishu 同步状态中存在失败和跳过记录，且 `job` 表当前全部为 `OPEN`。本轮不借去重或公司聚合之机改变岗位开放状态，也不因一次失败同步删除或关闭历史岗位。

## 8. 不在本轮范围内

## 9. 主要风险

1. `company_group_id` 的语义从 Feishu 记录变为真实公司，属于公共契约语义变化，需要同步架构、API、OpenAPI 和兼容策略。
2. 现有岗位已经有大量重复数据，合并可能影响收藏、推荐和外部链接，必须先做报告并保留来源证据。
3. 原始批次和规范招聘类型不是一一对应关系，产品文案必须避免把批次误称为唯一的规范招聘类型。
4. Feishu 当前存在失败同步记录，数据清理必须和采集完整性解耦。
5. 公司画像覆盖范围有限，未命中的公司只能按规范化名称精确聚合，不能在本轮引入未经验证的模糊合并。
