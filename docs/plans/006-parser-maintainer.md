# Parser Maintainer 实施计划

## 需求背景

当前岗位采集链路已经支持按链接类型选择解析器，并完成北森岗位解析、字段合并和入库。

目前的问题是：

* 其他已知平台尚未实现解析器；
* 后续还会出现未知平台或已有平台的新页面模板；
* 每次都由开发者重新调查接口、编写解析器和测试，重复成本较高；
* 解析器开发过程中积累的经验和踩坑记录没有形成可复用流程。

需要建立一套仅供开发者使用的 Parser Maintainer 工作流，让 Codex 按固定 Skill 调查解析失败样本，复用已有经验，完成解析器开发和验证。

## 目标

实现以下开发流程：

```text
采集流程记录无法解析的链接
→ 汇总并生成解析缺口报告
→ 开发者选择一个缺口
→ Codex 按 Parser Maintainer Skill 调查
→ 修正分类、扩展已有解析器或新增平台解析器
→ 补充 Fixture、测试和经验文档
→ 运行检查
→ 创建本地 Commit
→ 等待人工审核
```

本阶段由开发者手动触发，不做定时自动执行。

## 实现要求

### 1. 解析缺口输出

复用现有采集管线中的 `unsupported` 和失败信息，生成结构化解析缺口。

至少包含：

* 原始链接
* 当前分类
* 公司或来源
* 失败原因
* 失败类型
* 出现次数
* 少量代表样本

相同平台、域名和失败原因应能聚合，避免同类链接重复报告。

### 2. Parser Maintainer Skill

新增一个供 Codex 使用的 Skill，规定解析器开发的基本流程：

1. 阅读现有分类器、解析器、测试和经验文档；
2. 先判断是否分类错误；
3. 优先扩展已有平台解析器；
4. 只有确实是新平台时才新增解析器；
5. 优先寻找公开 API 或内嵌 JSON，再考虑 HTML；
6. 生成最小 Fixture 和测试；
7. 更新经验文档；
8. 运行项目现有质量检查；
9. 测试通过后创建本地 Commit。

Skill 必须要求使用 Ponytail 原则：

* 优先复用现有代码；
* 不新增没有必要的抽象；
* 不引入新的 Agent 框架；
* 不做无关重构；
* 使用最小改动解决真实问题；
* 不削减校验、错误处理和测试。

### 3. 经验沉淀

新增解析器经验文档，记录已经验证的经验，包括：

* 平台识别特征；
* 列表和详情数据入口；
* 分页方式；
* 字段映射；
* 已知页面模板；
* 遇到过的问题；
* 最终解决办法；
* 对应测试和 Fixture；
* 尚未支持的边界。

不保存完整聊天记录和模型思考过程。

### 4. 开发辅助脚本

提供最小开发入口，用于：

* 汇总解析缺口；
* 选取少量代表样本；
* 为 Codex 准备调查输入；
* 运行解析器相关检查。

具体脚本数量和组织方式由现有仓库结构决定，避免为此建立新的框架。

## 建议新增文件

具体命名可结合仓库现状调整，预计包括：

```text

docs/collection/parser-playbook.md
skills/parser-maintainer/SKILL.md

src/jobpicky/collection/parser_gaps.py
scripts/dev/report_parser_gaps.py
scripts/dev/verify_parser_change.py

tests/collection/test_parser_gaps.py
```

如果仓库已有 Skill 或开发脚本目录规范，应沿用现有规范，不重复建立目录。

可以对现有文件做最小修改：

```text
AGENTS.md
src/jobpicky/collection/pipeline.py
.gitignore
```

## 边界

本阶段不实现：

* 定时自动调用 Codex；
* 在生产服务中运行 Agent；
* 自动修改生产代码；
* 自动 Push 或创建 PR；
* 自动合并和部署；
* LangGraph 或多 Agent 系统；
* 通用解析器 DSL；
* ParserGap 数据库表和管理后台；
* 一次性实现所有招聘平台；
* 绕过登录、验证码、访问控制或反爬机制。

生产采集流程只负责记录解析缺口，不调用模型，也不修改代码。

Codex 可以修改当前开发分支、运行测试和创建本地 Commit，但不得 Push、创建 PR 或合并。

## 验收标准

1. 现有解析失败可以生成结构化缺口报告。
2. 同类失败可以聚合，并保留少量代表样本。
3. Parser Maintainer Skill 能指导 Codex完成解析器调查和开发。
4. 有独立经验文档用于复用已验证的方法和坑。
5. 至少使用一个真实未支持平台完整验证该流程。
6. 新解析器包含 Fixture 和自动化测试。
7. 北森现有解析和入库链路不受影响。
8. 项目现有 ruff、mypy 和 pytest 检查通过。
9. 未新增不必要的框架、依赖或公共契约。
10. 未自动 Push、创建 PR 或部署。
